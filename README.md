# Accessibility Fix Queue

A WCAG scan can be easy to run, but harder to act on. The real question isn't
whether a page has violations, it's which ones actually matter, whether forty
flagged elements are forty separate bugs or one repeated mistake, and what to
change to fix it.

This scans a live page with axe-core, the same engine behind Chrome DevTools,
then does what a free scanner doesn't: groups violations by shared root cause
instead of listing every instance separately, ranks the results by
real-world impact, and drafts a ticket for each cluster with the specific
fix, not just what's wrong, but exactly what to change to resolve it.

## How AI fits in

AI (Claude) does two things here, and nothing else.

**Clustering.** axe-core hands back a flat list of violations with no sense
of which ones are actually the same bug. Claude reads that list and decides
which violations share a real root cause, the same color token, the same
reused component, versus which ones just happen to trip the same axe rule
for unrelated reasons. Two different failing colors both called
`color-contrast` by axe need a human-like read to know they're not the same
fix, a simple string match on the rule id can't make that call.

**Ticket drafting.** Once grouped, Claude writes the actual ticket, title,
description, acceptance criteria, and the suggested fix, in plain language a
product team could act on without translating it themselves.

Everything else is deliberately not AI:

- **Detection** is axe-core, a real, industry-standard engine, not a model
  guessing violations from a screenshot.
- **Priority ranking** (the "priority 24 / 6 / 2" score on each ticket) is
  computed in code from severity weight x number of affected elements, not
  generated by the model.

That split was a real design decision made early on: let AI do the parts
that genuinely need judgment, keep everything else in plain, defensible
arithmetic wherever possible.

## Why not just use a free scanner?

WAVE, axe DevTools, and Lighthouse already do free, reliable WCAG scanning,
built by teams that specialize in exactly that. This isn't trying to out-scan
them. What none of them do is anything with the results beyond listing them,
a product team still has to figure out what to fix first and why. That's a
triage problem, not a detection problem, which is the actual gap this fills.

## Architecture

```
poc/        Task 1: axe-core scan + bounding boxes, validated locally
            against a real live URL before anything else was built.
ai-layer/   Task 2: the Claude clustering/prioritization/ticket layer,
            validated locally against real scan output.
frontend/   Task 3: the visual overlay + ticket card UI, built as a static
            prototype against real captured data.
worker/     Task 4: the Cloudflare Worker that ties it all together for a
            live, public "scan any URL" tool (Browser Rendering + axe-core
            + Claude, all in one request).
docs/       The live dashboard, served via GitHub Pages, calls the Worker.
```

Each stage was built and confirmed working on its own, against real data,
before being wired into the next one. Full build history, including the
real bugs hit along the way, is in the project journal.

## Cost

Detection and clustering together cost a fraction of a cent per scan
(claude-sonnet-5, ~4K input / ~1.5K output tokens for a typical page).
Cloudflare Browser Run's free tier covers roughly 20-60 scans a day, the
live demo is rate-limited per visitor to stay well inside that.
